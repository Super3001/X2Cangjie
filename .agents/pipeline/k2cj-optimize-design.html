kotlin2cj-optimize Skill 设计总览

1. 6-Stage Pipeline

每个目标通过以下 6 阶段流水线自动推进。所有修改在 translator 源码中进行，不修补 .cj 输出文件。

Pipeline 内有 优化循环（Optimization Loop）：外层一次性推进 Stage 1→3，内层 Stage 4→5→6 反复迭代直到收敛或卡住。

层级流程说明
外层
（一次性）		 1 Explorer  →  2 Translator  →  3 Compiler 发现目标 → 翻译 → 首次编译，获得错误基线。只执行一次
内层
（迭代循环）		 4 Diagnostician  →  5 Fixer  →  6 Verifier  ↺  4 诊断 → 修复 translator 源码 → 回归+重编译。有错误则回到 Stage 4，重复直到：
· errors = 0 → ✅ 收敛，切下一个目标
· 连续 2 轮无改善 → STUCK，切下一个目标

⚠ 关键规则：
1. Phase 0 先跑 — 任何 translator 修改后、翻译任何目标前，必须先 cargo test（187+33 全部通过），1 分钟确认无回归
2. 只改 translator 源码 — 所有修改在 engine.rs / parser.rs / render.rs 中完成
3. L1 优先 — 先尝试单文件小改，失败再升级到 L2/L3 多文件改动
4. 卡住即跳过 — 连续 2 轮无错误减少 → STUCK，自动切下一个目标
5. State 是唯一真相源 — 从 .claude/state/optimization-state.md 获取进度，不依赖 context 记忆

错误分类体系

Diagnostician 将所有编译错误归类到 6 大类（优先级从高到低）：

优先级类别含义修复手段示例
1 RENDER_GAP 翻译器渲染层缺失——已知语法映射但 render.rs 未实现 改 render.rs：为已知映射添加渲染分支 MutableMap 未渲染为 HashMap（查 hashmap.md 已知映射）
2 STDLIB_GAP Kotlin stdlib API 在仓颉无对应——需在 translator 实现 type mapping 改 stdlib_map.rs：新增 Kotlin→Cangjie 类型映射条目（L2） ThreadLocal → 无对应，需 stdlib_map.rs 新增映射
3 HEURISTIC_GAP 翻译器启发式规则不足——输出语法上正确但语义偏差 改 heuristics.rs 或多处联动：调整启发式转换逻辑（L1/L2） 默认参数 ! 标记未添加
4 PARSER_GAP Parser 不认识某个 Kotlin 语法结构 改 parser.rs：添加对该语法结构的识别规则（L1/L2） fun interface、..< range-until、expect/actual
5 NODE_GAP SOC 引擎问题——节点张力或级联传播异常 改 engine.rs：调整节点张力计算或级联收敛逻辑（L2/L3） 大文件（>20K 行合并）SOC 引擎收敛为空
6 UNCLASSIFIED 无法归类——需 LLM 自由裁量 LLM 自由研判后建议修改位置 —
Diagnostician 知识加载顺序（每轮 inner loop 调用时加载）：
1. kotlin-cangjie-patterns.md（项目私有，85 行模式快查）→ 2. Kotlin→Cangjie 规则（30 文件，一等知识源）→ 3. fix-history.md（避免重复修复）→ 4. Java→Cangjie 规则（补充 JVM 共享 API）→ 5. cangjie-dev 语言参考 → 6. x2cj-eval 评估标准

Round-Robin 轮换逻辑

读取 state/optimization-state.md：
  → 优先取当前 ⏳ (in-progress) 状态的目标
  → 按 Phase 顺序取下一个 🔒 目标：
    Phase 0 → 1a → 1b → 1c → 1d → 1e → 1f → 1g → 2a → 2b → 2c → 3a → 3b → 3c → 3d → 4a → 4b → 4c

收敛判定：
  Phase 0/1: G1 (0 编译错误) → ✅。不需要 x2cj-eval（子包无独立运行标准）
  Phase 2+:  G1 (0 errors) + G10 (x2cj-eval ≥ 75) → ✅

卡住判定：
  Inner loop 连续 2 轮无错误数减少 → 标记 STUCK，自动切下一个目标

#1 执行详情（ksoup-main，即 attemp-1）

这是难度梯度重设计之前对 ksoup 全量的首次尝试。当时 Pipeline 尚未定义子包拆分和跨项目轮换，目标是一次性将 ksoup 主模块（87 文件、~22000 行合并源码）翻译到 0 编译错误。

执行过程

阶段动作结果
诊断编译 100 个翻译产物 → 997 errors根因：var-func 命名冲突（Cangjie 不允许 let field: Type + func field(): Type 同名）
Engine 修复在 engine.rs 添加 resolve_var_func_collisions()错误 997→110（-887）
Renderer 修复处理 ::class/::method 引用 + Unicode surrogate chars错误 110→3（-107）
Parser 修复EOF tolerance：parse_class 末尾容错，Element.kt 从 1 字节 → 6670 字节消除 1870 级联错误
后处理编写 fix_all.py，30+ 模式自动修补 .cj 文件错误反复在 3↔1673 间震荡
Stub 攻坚战编译器驱动自动 stub 生成 + 编译顺序重排 + namespace flattening核心错误降至 ~15，但 stdlib stub 缺口导致级联 1598+

失败根因

剩余错误全是 Kotlin/Java stdlib 类型在仓颉无对应（MutableMap、MutableList、Entry、Regex、Charset 等）。手工 stub 陷入死循环：

泛型 stub（HashMap<K, V>）  →  override 级联不匹配  →  误差放大
非泛型 stub                →  API 契约断裂          →  类型错误扩散
嵌套类型（MutableMap.MutableEntry）→ stub 自身需要更多 stub

本质矛盾：后处理拿到的是已经丢弃了语言语义的纯文本。它不知道 MutableMap 在 Kotlin 里是 interface、有 get/put/remove、实参用了什么泛型——这些信息在翻译器渲染时已经丢失。结论：必须在 translator 里加 stdlib compatibility layer（L2/L3 级改动），在 AST→Cangjie 渲染阶段就把 MutableMap<K,V> → 仓颉 HashMap<K,V> 映射掉，带着完整类型信息走。

对后续 Phase 的影响
