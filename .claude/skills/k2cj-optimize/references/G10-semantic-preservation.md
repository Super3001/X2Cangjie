# G10 语义保持 — 用 x2cj-eval 替代运行时差分测试

## 为什么不用运行时差分测试

```
运行时差分测试:
  源项目有测试? → 跑Kotlin测试 → 翻译测试 → 跑Cangjie测试 → 对比
  源项目无测试? → 卡住
  测试依赖运行时环境? → 卡住
  单次运行 > 5分钟? → 太慢，阻塞loop
```

**太重**。目标库不一定有测试，有测试的不一定有仓颉运行时环境，有环境的跑一次要几分钟。这不是 loop 该做的事。

## x2cj-eval 的做法

不跑代码，**让 LLM 逐文件对比源和翻译产物**，从三个维度打分：

| 维度 | 满分 | 评估方式 |
|------|:--:|---------|
| **编译验证** (`cjpm build`) | 20 | 自动执行 |
| **LLM 语义评估**（5 子维度） | 30 | LLM 对比源/译文 |
| — 逻辑一致性 | 10 | 控制流、分支、循环是否一致 |
| — 实现完整性 | 10 | 方法/类/字段是否有遗漏 |
| — API 映射正确性 | 10 | 标准库 API 是否正确映射 |
| — 语义正确性 | 10 | 可空性、异常、并发语义是否等价 |
| — 幻觉代码控制 | 10 | 是否生成了源中没有的逻辑 |
| **LLM 性能评估**（6 子维度） | 15 | LLM 对比源/译文 |
| **LLM 代码质量评估**（3 子维度） | 15 | LLM 评估惯用法/异常/类型适配 |
| **总分** | **100**（跳过测试时归一化） | |

> 单元测试 (`cjpm test`) 可选：有就用（+20 分权重），没有就跳过，总分按编译+LLM三项归一化到 100。公式见 `~/x2cj-skills/skills/x2cj-eval/skill.md`。

## 为什么适合 kotlin2cj 的 loop

| 维度 | 运行时差分测试 | x2cj-eval（LLM 静态评估） |
|------|:---:|:---:|
| 要求源项目有测试 | ✅ 必须 | ❌ 不需要 |
| 要求仓颉运行时环境 | ✅ 必须 | ❌ 只需编译 |
| 单次耗时 | 分钟级 | 秒~十秒级（LLM 调用） |
| 覆盖率 | 只覆盖有测试的代码路径 | 覆盖所有翻译文件 |
| 发现的问题类型 | 运行时行为差异 | 语义/性能/质量差异 + 幻觉 |
| 适合 loop 节奏 | ❌ 太慢 | ✅ 轻量，不阻塞 |

## Guard: 3.5-semantic-guard.md 修改

```
PASS: 总分 ≥ 75（满分100，≥75%）→ 语义保持可接受
FIX:  总分 50-74 → 语义漂移，返回 Stage 4 诊断
CRITICAL: 总分 < 50 → 大面积语义错误，暂停 loop，标记人工审查
SKIP:  无 .cj 文件对可评估 → 标记 WARNING，不阻塞
```

## 与运行时测试的关系

x2cj-eval **不是替代**运行时测试，是**优先使用**。如果目标恰好有测试套件且环境可用，运行时测试仍然是最强验证（T_verify 的黄金标准）。x2cj-eval 是"轻量默认"，运行时是"可选增强"——符合慢驱动的节奏要求：不让验证环节成为 loop 的瓶颈。
